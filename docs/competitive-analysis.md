# 竞品对照与能力取舍

> 日期：2026-11-01
> 参考对象：观测云（guance.com）、Datadog、Dynatrace、Grafana LGTM、SigNoz、夜莺 n9e。
> 目的：说明「哪些能力必须有、哪些本轮补齐、哪些明确不做」，避免范围失控。
> 关联：[feature-gap-design.md](feature-gap-design.md)、[user-guide.md](user-guide.md)、
> [guance-benchmark.md](guance-benchmark.md)（观测云逐项对标与本轮落地）。

## 1. 一句话定位

竞品做的是「大而全的可观测平台」，本项目做的是**局域网、离线、C++ 多进程系统的
最短排障路径**：

> 输入 `request_id` / `trace_id` / `task_id` / 错误码 → 还原跨进程调用链 →
> 关联每个环节的日志与错误 → 给出可疑根因与证据包。

因此判断标准不是「功能数量对齐」，而是：**现场排障时，从发现异常到拿到可复核证据
需要几步**。

## 3. 关键能力的对照说明

### 3.1 调用链：跨进程 + 进程内

- 观测云 / Datadog / Dynatrace：自动插桩覆盖广，语言与框架生态强；
- 本项目：聚焦 C++，通过 SDK 的 RAII Span、W3C `traceparent` 与
  `create_span_with_parent` 完成跨进程续接；进程内函数级 Span 与线程事件环
  同属一条 trace；
- 差异：不做 gRPC streaming/异步拦截、eBPF 自动弱边；A 语言栈以外不覆盖。

### 3.2 日志治理

竞品的核心是「采集 → 解析 → 检索 → 告警」全链路；本项目把重点放在**降噪**：

- 错误日志 100% 保留，INFO 按比例采样；
- 同指纹 60 秒窗口去重；
- 噪声模板只计数不存储；
- 模板聚类 + 指纹下钻；
- 动态日志级别（带 TTL）避免长期开 DEBUG。

这些能力在观测云/Datadog 中都有对应物，但本项目把「默认少收、错误多留」作为
默认策略，适配内网存储有限、日志量大的现场。

### 3.3 SLO 与错误预算

- 竞品通常支持多 SLI、多窗口、多燃烧率告警；
- 本项目简化成两类 SLI（可用性、延迟）与单窗口燃烧率；
- 理由：局域网试点阶段先保证「看得懂、能闭环」，复杂 SLO 配置反而增加使用门槛。
  计算基于中心当前内存 trace 窗口，重启后短暂 `unknown`。

### 3.4 拓扑：强边与弱边分离

Dynatrace 的自动依赖发现是竞品标杆；本项目不做自动发现，而是：

- gRPC/Socket 显式传播产生的边是强边，进入 Span 树结论；
- 推断边标记 `confidence`，只进拓扑图，不污染调用链；
- 这与计划书中的「强弱边分离」原则一致，避免自动推断误导根因。

### 3.5 Profiling

- 观测云/Datadog/Pyroscope 提供常驻 CPU/内存/锁/IO 采样；
- 本项目当前只做**折叠栈导入 + 聚合 + 火焰图 + Top self/inclusive**，
  不做进程内 `SIGPROF` 采样（避免影响生产环境），也不做常驻采集；
- 需要时由诊断命令按需触发，结果进入证据包。

### 3.6 崩溃诊断

这是本项目相对轻量竞品的差异点：

- SDK async-signal-safe 崩溃报告 → Agent 收集上传 → 服务端指纹聚合 →
  `addr2line` / `llvm-symbolizer` 离线符号化；
- 崩溃进入事件中心，可关联 trace 与 build_id；
- 竞品多依赖平台侧 core 收集，本项目把「离线、内网、无外部依赖」放在第一位。

### 3.7 证据包与 MCP

观测云有「异常追踪 + AI 助手」，Datadog 有 Bits AI，Dynatrace 有 Davis；
本项目的差异是**证据包可带走**：

- 一个自包含目录（manifest + timeline + request + metrics + logs + profiles +
  dumps + index + hypotheses），带 SHA-256 与脱敏规则；
- 内部的 `vmon_mcp` 提供只读工具，让 Claude Code 等工具在授权范围内查询；
- 不进入对外发行包，避免把内部数据能力带出去。

| 能力 | 本轮动作 | 验收 |

| Trace 瀑布图 | 树/关键路径/瀑布并列 | UI 回归；修复未结束 Span 负时长 |
| 日志过滤 | node/task_id/时间窗 | E2E + UI |
| 规则表单 | 常用字段表单 + JSON 高级编辑 | UI 回归 |
| 统一搜索 | `q` 覆盖 trace/request/task/服务/Span | 单测 + E2E + UI |

| 告警通知 | 事件 Webhook（异步、有界队列、失败计数） | 单测 |
| 文档 | 使用手册、快速诊断、场景手册、模块/类/时序图、竞品分析、UI 测试报告 | 本目录文档 |

## 5. 明确不做（本期）

| 能力 | 理由 |
|---|---|
| 公网 SaaS、多租户、角色权限 | 纯内网私有部署，规模 10–50 节点 |
| RUM、Session Replay、移动端 | 目标系统是 C++ 后端 |
| K8s/多云资产、云成本、SIEM | 与离线局域网场景无关 |
| 拨测/合成监控 | 需要外部目标与网络策略，二期评估 |
| 邮件 / syslog 通知 | Webhook 已实现；邮件/syslog 需要额外配置与网络策略，二期 |
| DQL/类 SQL 查询语言 | 当前查询 API 已覆盖排障路径，避免自造语言 |
| 常驻 CPU `SIGPROF`、eBPF、gRPC streaming 拦截 | 避免影响生产；按需诊断优先 |
| ClickHouse/VictoriaMetrics 强依赖 | 试点规模内存 Store 足够；预留转发接口 |

## 6. 结论

与竞品相比，本项目不追求「采集器数量、语言覆盖、云原生集成」的广度，而是在
**局域网 C++ 系统**这一窄场景里，把以下闭环做完整：

```
发现异常 → 看链路/指标 → 定位服务与节点 → 关联日志 → 确认/关闭事件 →
需要时导出证据包 → 交给内部 AI 复核
```

竞品有而本项目暂缺的能力，已在第 5 节显式列为非目标或二期，避免验收时产生
「功能缺失」的误解；竞品有且属于排障刚需的能力（指标、SLO、事件闭环、拓扑、
瀑布图、日志过滤、规则表单），本轮已补齐并有测试覆盖。
